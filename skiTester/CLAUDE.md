# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository scope

This directory (`skiTester/`) is the ESP32 firmware for the ski glide tester's measurement device, one part of a larger `skiTester` monorepo (`/Users/reetu/Dev/skiTester`) that also contains:
- `swiftApp/SkiTesterApp/` — the iOS SwiftUI client this firmware talks to over BLE (see its own `CLAUDE.md`; the source of truth for the BLE message protocol as consumed by a client)
- `circuit/` — KiCad PCB design files
- `3d_models/` — enclosure/mount models
- `reactNativeApp/` — an inactive alternate client (per the repo README, only the SwiftUI app is under active development)

The device measures ski glide performance: a skier passes through two magnet gates, and the firmware times the run and averages the linear acceleration magnitude sampled during it, then reports both over BLE.

## Build, flash, monitor

PlatformIO project, single environment `dfrobot_firebeetle2_esp32e` (Espressif32/Arduino framework), defined in `platformio.ini`.

```bash
pio run                  # build
pio run -t upload        # build and flash
pio device monitor       # serial monitor (115200 baud)
pio run -t upload -t monitor   # flash then immediately open monitor
pio run -t clean         # clean build artifacts
```

There is no test suite — `test/` contains only PlatformIO's scaffold README, no actual tests.

Library deps (`lib_deps` in `platformio.ini`): `ArduinoJson`, `Adafruit_BNO08x` (IMU), `NimBLE-Arduino` (BLE stack). `.vscode/c_cpp_properties.json` is auto-generated by the PlatformIO IDE extension from these — don't hand-edit it.

## Architecture

Four files in `src/`, wired together in `main.cpp`:

- **`config.h`** — shared constants: pin assignments (`SENSOR_PIN` = magnet gate interrupt, `BUZZER_PIN`, `BNO08X_CS`/`_INT`/`_RESET` for the SPI IMU), sampling params (`measurement_interval` Hz × `max_measurement_time` s sizes the acceleration ring buffer), and the `StatusCode` enum used on the BLE wire protocol.
- **`imu_sensor.cpp/.h`** — thin wrapper around `Adafruit_BNO08x`: `imuBegin()` starts SPI, `setReports()` enables the `SH2_LINEAR_ACCELERATION` report, `getLinearAcceleration()` polls one sensor event.
- **`ble_server.cpp/.h`** — NimBLE peripheral exposing a Nordic UART-style service (`6E400001-...`) with a notify characteristic (TX, `...0003`) and a write characteristic (RX, `...0002`). `notifyClients(status, mag_avg, total, message, imu_cal)` is the only way results/errors/state reach the phone: it serializes a JSON doc (`{"status", "id", "time", "mag_avg", "imu_cal", "message"}` — fields populated per status) and notifies over TX. Every outbound message gets a monotonically increasing `id` (`nextMsgId`), which the app ACKs by writing `{"id": ...}` back to RX (`RxCallbacks::onWrite` just logs these acks — no retry-on-missing-ack logic exists). `RxCallbacks::onWrite` also handles `{"cmd":"clear"}` from the phone by setting a `clearRequested` flag, consumed once per `loop()` via `consumeClearRequest()` to reset measurement state. Advertises as `"SkiTester"` and restarts advertising on disconnect so the app can reconnect; sends `STATUS_IDLE` on `onConnect`.
- **`main.cpp`** — the state machine, entirely `loop()`-driven (no RTOS tasks):
  - `mittaa()` is an `IRAM_ATTR` ISR on `SENSOR_PIN` FALLING edge (a magnet passing the gate), debounced to >1s between triggers. It toggles `measuring` and stamps `start_time`/`end_time` — first trigger starts a run, second ends it.
  - Every `loop()` iteration polls the IMU once (`getLinearAcceleration`, now also returning an `accuracy` field from `sh2_SensorValue_t.status`); while `measuring` and no `end_time` yet, the acceleration magnitude (`sqrt(x²+y²+z²)`) is accumulated into `mag_buf`, a fixed-size array sized by `MAG_MAX = measurement_interval * max_measurement_time`. Whenever `accuracy` changes from `last_imu_accuracy`, a `STATUS_IMU_STATUS` notification is sent regardless of measuring state.
  - When `end_time` is set, `loop()` averages `mag_buf`, calls `notifyClients(STATUS_RESULT, mag_avg, elapsed_seconds)` followed by `notifyClients(STATUS_IDLE)`, and resets state for the next run. The same `STATUS_ERROR` → `STATUS_IDLE` sequence happens on error.
  - A 30s timeout (`MEASUREMENT_TIMEOUT_MS`) aborts a stuck `measuring` state and surfaces `errorMessage` via `STATUS_ERROR` on the next `loop()` pass.
  - `start_event`/`measuring`/timestamps are `volatile` since they're written from the ISR and read from `loop()`.

**Wire protocol:** `config.h`'s `StatusCode` (`STATUS_IDLE`=0, `STATUS_START`=1, `STATUS_RESULT`=2, `STATUS_ERROR`=3, `STATUS_IMU_STATUS`=4) now matches the iOS client's `StatusCode` enum (`swiftApp/SkiTesterApp/AppState.swift`) exactly, and the `id`/ack and `{"cmd":"clear"}` handshakes the app already implemented (`BLEManager.sendAck`/`sendClear`) are now acted on by the firmware. When changing either side, keep both in sync — there's no shared schema, just matching hand-written structs.

## Conventions to know

- Comments and log-adjacent user-facing strings in this codebase are in Finnish (matches the Finnish UI strings in the iOS app); keep new comments consistent with this.
- `ble_server.cpp`'s `notifyClients`/`initBLE` are described in comments as "same signature as before" — this file was refactored from an earlier BLE implementation; check `ble_server.h` for the current public API rather than assuming.
